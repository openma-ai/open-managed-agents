# Default Pi mixed-batch regression gates

These local gates use the current `PiHarness`, production Session/Work paths and
persisted history. They do not certify a cloud provider or a deployed topology.
The `platform-parity` goldens are generated by the Pi host loop. Their masked
Cloudflare test-double outputs are supplementary regression coverage only.

Run the Node gate from `apps/main-node`:

```sh
../../node_modules/.bin/vitest run --config vitest.config.ts test/mixed-process-restart.test.ts
```

It uses two real Node processes in succession, SIGKILL after park, SQLite,
actual bash filesystem effects and a loopback HTTP MCP tool. Four cases cover
custom before/after ordinary tools, MCP, and multiple custom tools. Two rounds
check partial, duplicate and late first-round answers, legal model history,
pre-park persistence, model-call counts/timing and no repeated side effects.

Run the Cloudflare gate from the repository root:

```sh
node_modules/.bin/vitest run test/integration/pi-mixed-restart.cf.test.ts
```

It uses Workerd SessionDO/D1 and a controlled post-park DO crash, then a fresh
stub. A loopback-only peer executes one fixed bash program and an MCP tool with
real filesystem effects. It cannot execute arbitrary programs and never calls
an inference provider. The configured Sandbox fixture supplies lifecycle only;
this is not an SDK native-container test. No output-content mask is applied.
The multiple-custom case also checks late answers against a distinct second
round. The reader requests the full event page rather than confusing the
20-event default page with missing terminal events.

Provider failure continuation has separate Node and Workerd gates:
`apps/main-node/test/provider-failure-continuation.test.ts` and
`test/integration/provider-failure-continuation.test.ts`. They require a single
correlated error, the model observing `isError: true`, a subsequent successful
action, and one normal `end_turn`, while custom waits remain unsatisfied.
Preparation failures have separate preflight tests; they are not tool-job tests.

Actual isolated deployments and live-provider fault tests require separate
receipts tied to the reviewed source candidate. Passing these commands must
not be represented as four-topology acceptance.
